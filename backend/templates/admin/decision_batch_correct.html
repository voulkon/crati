What this does

Every detector declares its own candidate query, so the bounds below mean slightly different things: the decimal separator shift detector compares the min/max amount against the decision's computed total, while the non-monetary value detector compares them against the individual recorded amount.

  1. Decimal separator shift (needs the document text):
    1. Reads the actual document text for each candidate — if a decision has no extracted text yet and “Read if missing” is checked, the document is downloaded and extracted first.
    2. Uses the cents-based detector to find monetary amounts in the text (numbers ending with ,00, ,50, etc. — the defining signal of money in Greek documents).
    3. For each DecisionAmountField row whose value is NOT found verbatim in the text but HAS a ×100 or ÷100 clone, stores the corrected value in verified_amount.
  2. Non-monetary value (database-only, no document read): compares each recorded amount against the decision's own AFM (VAT number) and KAE (budget code) values. The real amount is unknown, so the row is flagged — never written to verified_amount. Flagged decisions appear in the flagged pool for manual follow-up.
  3. All downstream consumers use COALESCE(verified_amount, amount) so corrected values automatically override the erroneous metadata everywhere — API filtering, pre-calc rankings, statistics. Flagged rows are excluded from every monetary aggregation.

Tip: Use Dry Run first to preview what would be corrected before making changes.
